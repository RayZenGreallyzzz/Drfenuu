# Personal release signing and updates

Run `bash tools/create-signing-key.sh` locally (requires Java keytool; Termux with a JDK is an option). Choose a strong unique password. Keep an offline backup of the PKCS12 file and password.

In GitHub repository Settings > Secrets and variables > Actions > New repository secret, create:
- AETHER_KEYSTORE_B64: exact single-line contents of keystore-base64.txt
- AETHER_KEYSTORE_PASSWORD: password chosen during key generation.

Never put either value in a public file, issue, message or commit. The signing key is not generated by CI. Re-run the latest Gecko Edition workflow after adding both secrets. Only the gecko-edition branch produces a signed release, using ARM64. When both secrets are configured, the Gecko branch skips debug APK publication so users cannot accidentally install the wrong signer. Without secrets the build produces an ARM64 test APK only; it is not a stable update channel. Keep control of repository write access and review workflow changes before signing.

The earlier debug APK is normally signed by an ephemeral debug key. It cannot be updated in place using the new key unless the certificates happen to match. Export important data before uninstalling, and keep original ZIP/JS archives. Subsequent releases must increment versionCode and use the same key and application ID.

This stage provides stable signing and an ABI-specific APK. Local .aeb delta reconstruction and installation are implemented experimentally; automatic downloads, patch publication and data migration are not. Delta patches must reconstruct the exact new signed APK, validate base and target hashes, verify signer and version, and fall back to full APK when needed. Android still requires user confirmation for sideloaded updates.
